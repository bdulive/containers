# bitnami/rabbitmq

## Directory roles

| Path | Role |
| --- | --- |
| `4.3/debian-12/` | **Generated by the Bitnami release pipeline. Do not hand-edit.** Any change here is overwritten on the next `[bitnami/rabbitmq] Release ...` commit from `upstream`. |
| `4.3/debian-13/` | Hand-maintained CVE-remediated variant. This is where local fixes go. See its `README.md` for the change list and CVE map. |
| `4.2/`, `config/`, `docker-compose*.yml` | Upstream-generated. Leave alone. |
| `prebuildfs/opt/bitnami/scripts/lib*.sh` (inside each variant) | Shared Bitnami shell libraries, vendored per image. Edits are local to that one variant. |
| `rootfs/opt/bitnami/scripts/librabbitmq.sh` | RabbitMQ-specific logic: config generation, plugin download, password hashing, cluster join. |
| `prebuildfs/opt/bitnami/checksums/` | `sha256` files for the components the Dockerfile downloads. One file per component per arch; a component removed from the Dockerfile must have its checksum file removed too, or the build silently carries dead metadata. |

## Image composition

Both variants assemble the same three pieces:

1. A `bitnami/minideb` base (`bookworm` for debian-12, `trixie` for debian-13).
2. Prebuilt component tarballs from `https://downloads.bitnami.com/files/stacksmith`,
   named `<name>-<version>-<revision>-linux-<arch>-<flavour>.tar.gz`, unpacked to
   `/opt/bitnami` with `--strip-components=2`.
3. `prebuildfs` and `rootfs` overlays, then `postunpack.sh`.

Facts worth not re-deriving:

- **The RabbitMQ component contains zero native objects** (`tar -tzf ... | grep -c '\.so'` is 0). It is pure BEAM, so it is portable across Debian releases and across Erlang patch levels. This is why debian-13 reuses the `debian-12` RabbitMQ tarball.
- **Perl is not used at runtime.** `replace_in_file` uses `sed`; only `replace_in_file_multiline` used `perl`, and nothing calls it. The `perl` hits in `rabbitmq-server` are the word "properly".
- **`curl` is used at runtime** in exactly three places: `librabbitmq.sh` (community plugin download), `rabbitmq/apicheck.sh`, and `libnet.sh` (`wait_for_http_connection`). `wget` covers all three; `file://` URLs need a `cp` branch because GNU wget cannot read them.
- **The `openssl` CLI is used at runtime** by `rabbitmq_hash_password` (`openssl dgst -sha512`, `openssl base64`), so the `openssl` package cannot be dropped — only `libssl3` would be enough for Erlang.
- `rabbitmq_erlang_dir()` resolves as `dirname(dirname(which erl))`, so any Erlang installed at `/opt/bitnami/erlang` with a standard `bin/` + `lib/erlang/` layout works, including a source build with `--prefix=/opt/bitnami/erlang`.

## CVE remediation workflow

Work in this order; each step tells you whether the next is even needed.

1. **Check what a rebuild would fix.** Query the Debian tracker per CVE and read the
   per-suite rows, not the description:
   `curl -sS https://security-tracker.debian.org/tracker/CVE-YYYY-NNNNN`
   A `bookworm (security) | <ver> | fixed` row means a plain rebuild is the fix.
   `vulnerable` on every suite means **no Debian fix exists** and the only options
   are removing the package or changing base release.
2. **Check what components exist before assuming a bump is possible.** Bitnami
   publishes components for base releases only. Probe before planning:
   `curl -o /dev/null -w '%{http_code}' https://downloads.bitnami.com/files/stacksmith/erlang-<ver>-<rev>-linux-amd64-debian-12.tar.gz.sha256`
   Do not trust a version number in a tarball name — download it and read
   `lib/erlang/releases/*/OTP_VERSION`. Bitnami's `erlang-28.5.0-0` reports `28.5`,
   which is *older* than the `28.5.0.4` several advisories require.
3. **Erlang advisories are almost always fixed only in four-component patch
   releases** (`27.3.4.15`, `28.5.0.4`, ...) that Bitnami does not package. The
   remedy is the source build in `4.3/debian-13/Dockerfile`: bump `OTP_VERSION`
   and `OTP_SRC_SHA256`. Newest tag on a line:
   `curl -o /dev/null -w '%{http_code}' https://api.github.com/repos/erlang/otp/git/ref/tags/OTP-27.3.4.18`
   Stay on the OTP minor line the RabbitMQ component was built against.
4. **Keep component metadata accurate when replacing a component.** A source-built
   Erlang must still write `/opt/bitnami/erlang/.spdx-erlang.spdx`, or scanners
   report nothing for the runtime instead of reporting it as clean. The Dockerfile
   generates it from `OTP_VERSION`.
5. **Removing a package is a legitimate fix, but check the runtime first** (see the
   facts above) and keep `dpkg --purge` of anything Essential as the **last**
   dpkg/apt step of the build — debconf-driven maintainer scripts need perl.

## Build and verify

```console
cd 4.3/debian-13
docker build --provenance=false --sbom=false -t bitnami-rabbitmq:4.3.5-debian-13-r0 .
```

`--provenance=false --sbom=false` matters: with default attestations, Docker 29
writes an OCI layout that Trivy 0.74 rejects with `archive/tar: invalid tar header`.

A cold build compiles Erlang and takes 15-25 minutes; on Apple Silicon build
`linux/arm64` natively and confirm package names/versions separately on amd64
rather than emulating.

Scan. Neither Trivy nor Docker Scout can read the daemon's image directly here
(Docker 29's OCI layout - `archive/tar: invalid tar header`), so go through the
exported filesystem:

```console
docker create --name probe bitnami-rabbitmq:4.3.5-debian-13-r0
mkdir fs && docker export probe | tar -x -C fs && docker rm -f probe

grype db update && grype dir:fs                    # primary
trivy rootfs --scanners vuln --severity CRITICAL,HIGH fs
docker scout cves --only-severity critical,high fs://fs
```

**Use grype as the primary scanner.** DB coverage of the 26 CVEs this variant was
built to clear differs wildly: grype 23/26, Docker Scout 9/26, Trivy 4/26. A clean
Trivy run proves almost nothing here; a grype before/after against the debian-12
baseline is the real evidence. Some CVEs (the three `libssh2` ones) are in no
database yet and can only be verified by the package being absent - always pair a
scan with the per-package checks in the variant's README.

Treat a finding as actionable only if a fix exists - `FixedVersion` in Trivy,
fix state `fixed` in grype. The pass condition is **zero fixable findings**, not a
zero total: the residual findings in this image are all `wont-fix`/`not-fixed`
in Debian 13.

Smoke test:

```console
docker run -d --name rmq -e RABBITMQ_PASSWORD=bitnami123 -e RABBITMQ_LOGS=- bitnami-rabbitmq:4.3.5-debian-13-r0
docker exec rmq rabbitmq-diagnostics -q check_running
docker exec rmq rabbitmq-diagnostics -q check_port_connectivity
docker exec rmq rabbitmq-diagnostics -q status | grep -E 'RabbitMQ version|Erlang configuration|Crypto library'
docker exec rmq cat /opt/bitnami/erlang/lib/erlang/releases/27/OTP_VERSION
```

Publish/consume through the management API (also exercises the `wget` conversions),
and confirm the removals actually held:

```console
docker exec rmq bash -c 'command -v perl; command -v curl; find / -name "libssh2*" 2>/dev/null | wc -l'
```

Expect no perl, no curl, and `0`.

## Upstream sync

`origin` is the fork, `upstream` is `bitnami/containers`. When pulling upstream
releases, `4.3/debian-12/` will move and `4.3/debian-13/` will not. After a
RabbitMQ release bump, re-diff the two variants
(`diff -ru 4.3/debian-12/rootfs 4.3/debian-13/rootfs`) so the four local script
changes stay rebased onto the new upstream scripts, and update the component
version and checksums in the debian-13 Dockerfile and `prebuildfs/.../checksums/`.
