# bitnami/rabbitmq

## Directory roles

| Path | Role |
| --- | --- |
| `4.3/wolfi/` | **The only hand-maintained variant.** RabbitMQ 4.3.5 on `cgr.dev/chainguard/wolfi-base`. All local remediation goes here. See its `README.md` for the change list and CVE map. |
| `4.3/debian-12/` | **Generated by the Bitnami release pipeline. Do not hand-edit.** Any change here is overwritten on the next `[bitnami/rabbitmq] Release ...` commit from `upstream`. |
| `4.2/`, `config/`, `README.md`, `docker-compose*.yml` | Upstream. Leave byte-identical so the fork keeps merging cleanly. |
| `prebuildfs/opt/bitnami/scripts/lib*.sh` (inside each variant) | Shared Bitnami shell libraries, vendored per image. Edits are local to that one variant. |
| `rootfs/opt/bitnami/scripts/librabbitmq.sh` | RabbitMQ-specific logic: config generation, plugin download, password hashing, cluster join. |
| `prebuildfs/opt/bitnami/checksums/` | `sha256` files for the components the Dockerfile downloads. One file per component per arch; a component removed from the Dockerfile must have its checksum file removed too, or the build silently carries dead metadata. |

**Wolfi is where every future CVE fix goes.** A `4.3/debian-13/` variant on
`minideb:trixie` existed until 2026-09-17 and was deleted — it could not clear the
acl/attr advisories on any Debian base, it needed an Erlang source build and a `perl`
force-purge that Wolfi makes unnecessary, and it scanned 189 findings against Wolfi's 1.
Do not recreate a Debian-based variant to carry a fix. The reasoning that variant
accumulated is preserved in the sections below, rewritten for the base we actually ship.

## Image composition

The wolfi variant assembles three pieces:

1. `cgr.dev/chainguard/wolfi-base`.
2. Prebuilt component tarballs from `https://downloads.bitnami.com/files/stacksmith`,
   named `rabbitmq-<version>-<revision>-linux-<arch>-debian-12.tar.gz`, fetched and
   checksum-verified in a **separate build stage** so `wget`'s dependency chain never
   reaches the runtime image, then unpacked to `/opt/bitnami` with `--strip-components=2`.
3. `prebuildfs` and `rootfs` overlays, then `postunpack.sh`.

Facts worth not re-deriving:

- **The RabbitMQ component contains zero native objects** (`tar -tzf ... | grep -c '\.so'`
  is 0). It is pure BEAM, so it is portable across distributions and across Erlang patch
  levels. This is why the wolfi variant reuses the `linux-<arch>-debian-12` tarball
  unmodified — Bitnami publishes no Wolfi components, and none are needed. Note the gap:
  the Dockerfile asserts the *Erlang* version and runs `erl`, but unlike the redis-cluster
  variant it runs no component-level check, so a broken component surfaces at first boot
  rather than at build time. Add one if you ever touch the component version.
- **Erlang comes from `apk`, not from source.** Wolfi's `erlang-27` is exactly 27.3.4.17,
  the OTP patch release several advisories require and Bitnami publishes no component for.
  It installs to `/usr/lib/erlang` and is **symlinked** to `/opt/bitnami/erlang` — a
  symlink, not a copy, so apk keeps owning the files and the SBOM keeps reporting the
  package. The build fails if `apk info -v` resolves anything other than `${OTP_VERSION}`;
  a silent downgrade would reintroduce fixed OTP advisories.
- `rabbitmq_erlang_dir()` resolves as `dirname(dirname(which erl))`, so any Erlang with a
  standard `bin/` + `lib/erlang/` layout under `/opt/bitnami/erlang` works — including the
  symlinked apk install.
- **Perl is not used at runtime, and Wolfi installs none.** `replace_in_file` uses `sed`;
  only `replace_in_file_multiline` used `perl`, and nothing calls it. The `perl` hits in
  `rabbitmq-server` are the word "properly". Locales come from `glibc-locale-en`, so there
  is no `locale-gen` and therefore no perl to purge.
- **`wget` *is* in the runtime image here, deliberately.** Unlike redis-cluster, rabbitmq
  has three real runtime HTTP call sites: `librabbitmq.sh` (community plugin download),
  `rabbitmq/apicheck.sh`, and `libnet.sh`'s `wait_for_http_connection`. `wget` covers all
  three; `file://` URLs need a `cp` branch because GNU wget cannot read them. This is why
  this image — unlike redis-cluster — carries four script-level changes; see **Upstream
  sync**.
- **The `openssl` CLI is used at runtime** by `rabbitmq_hash_password`
  (`librabbitmq.sh:807-808`: `openssl dgst -sha512`, `openssl base64`). It is *not* in the
  Dockerfile's `apk add` list — it arrives as a dependency of `erlang-27`. Anything that
  changes the package set must re-check `command -v openssl`, or password hashing breaks at
  first boot with no build-time warning.
- `getent` comes from `posix-libc-utils-bin` (used by `libnet.sh` and `libos.sh`).
- `wolfi-base` only ships `nonroot` (65532); uid 1001 is created explicitly.
- prebuildfs helpers live under `usr/bin`, not `usr/sbin` — Wolfi symlinks `/usr/sbin` and
  `/sbin` to `usr/bin`, and `COPY` cannot write through a symlinked directory.
  `install_packages`/`uninstall_packages` are rewritten against `apk` with the same
  contract.

## CVE remediation workflow

Work in this order; each step tells you whether the next is even needed.

1. **Check the Wolfi secdb before anything else.** Wolfi's fix for an advisory is usually
   already packaged, and often under a version string the scanner does not expect:

   ```console
   curl -sS https://packages.wolfi.dev/os/security.json | \
     jq '.packages[] | select(.pkg.name=="<pkg>") | .pkg.secfixes'
   ```

   If the secdb names a fixed version at or below what `apk` installs, a plain rebuild is
   the fix — and if the scanner still reports it, see the zlib section below before
   touching the Dockerfile.
2. **Rebuild first.** `apk upgrade --no-cache` runs in the Dockerfile, so a rebuild picks
   up every published fix. Bump `IMAGE_REVISION` and the `-r<n>` tag; that is the whole
   change for most advisories.
3. **Check what Bitnami components exist before assuming a component bump is possible.**
   Bitnami publishes for base releases only. Probe before planning:
   `curl -o /dev/null -w '%{http_code}' https://downloads.bitnami.com/files/stacksmith/rabbitmq-<ver>-<rev>-linux-amd64-debian-12.tar.gz.sha256`
   Do not trust a version number in a tarball name — download it and read
   `lib/erlang/releases/*/OTP_VERSION`. Bitnami's `erlang-28.5.0-0` reports `28.5`, which
   is *older* than the `28.5.0.4` several advisories require.
4. **Erlang advisories are almost always fixed only in four-component patch releases**
   (`27.3.4.15`, `28.5.0.4`, ...). Check what Wolfi has packaged first — `apk info -v
   erlang-27` in a throwaway container, or the apk index — and bump `OTP_VERSION` in the
   Dockerfile to match. Stay on the OTP minor line the RabbitMQ component was built
   against. Only if Wolfi lags the needed patch release does a source build come back on
   the table, and it should be argued for explicitly rather than assumed.
5. **Read an advisory's affected range against the *upstream* version, not a distro's.**
   Distro matchers key on the suite: a feed with no fixed version flags the package at
   *any* version with no `FixedVersion`. Confirm with
   `trivy rootfs --format json fs | jq '.Results[].Vulnerabilities[]? | select(.VulnerabilityID=="CVE-...")'`
   before concluding an upgrade failed.

### CVE-2026-85091 (zlib): fixed in the package, still reported by Trivy

The `-r0` Wolfi image shipped `zlib 1.3.2-r6`, inside the advisory's range, with the fix
named as a version (`1.3.3-r0`) that had not reached the apk repo. **That identifier was
superseded.** Chainguard backported the fix instead — upstream `madler/zlib` commit
`df84af25dc` ("Fix buffer overflow bug in non-blocking gzwrite"), carried as
`0001-gz_write-don-t-keep-a-pointer-into-callers-buffer-on.patch` in `zlib.yaml` — and both
`packages.wolfi.dev/os/security.json` and `packages.cgr.dev/chainguard/security.json` now
name the fixed version as **`1.3.2.1_rc20260601-r0`**, which is what `apk` installs today.
The `-r1` rebuild (2026-09-17) carries it, and Docker Scout reports 0 findings on it.

**Do not wait for a zlib 1.3.3 package.** Upstream has no such tag; `v1.3.2` is the newest,
and `1.3.2.1_rc20260601` is a develop-branch snapshot Chainguard versioned with an `_rc`
suffix deliberately so a future real 1.3.2.1 sorts above it.

Trivy 0.74 still emits the row: its DB (built 2026-09-16 19:39 UTC) carries the stale
`1.3.3-r0` fixed-version, above the installed one. This is scanner-DB lag, not package
state. Before treating it as a real finding, refresh the DB (`trivy image
--download-db-only`) and compare the installed version against the secdb query in step 1.

Do not pin zlib backwards to dodge any of this: `1.3.1.2-r3` is still inside the range
*and* adds CVE-2026-27171.

### Do not retry: swapping the GNU userland for applets

Prototyped and rejected on 2026-09-14, when the goal was shedding `libacl1`/`libattr1` on a
Debian base. **On Wolfi the premise is gone** — `coreutils`, `sed`, `grep` and `gawk` pull
the *patched* acl 2.4.0 / attr 2.6.0, so the GNU userland costs nothing in CVE terms and is
installed deliberately. The measurements are kept because the conclusion generalises:

| replacement | scanner total / CRITICAL / HIGH (grype, pre-2026-09-15, on the Debian base) | verdict |
| --- | --- | --- |
| none | 139 / 0 / 44 | the three acl/attr rows are reported |
| busybox 1.37.0 | 140 / 0 / 50 | rows gone, but busybox adds **14 advisories of its own, 8 HIGH, all wont-fix** |
| toybox 0.8.9 | 126 / 0 / 42 | rows gone, toybox carries **zero** CVEs — but it has no `tr` or `dd` |

toybox was the only version worth having and it could not ship: the Bitnami scripts use
`tr` on live paths and the failure is **silent**. `run.sh` parses `REDIS_NODES` through
`tr`, so the container still starts and the service still boots, with an empty node list.
Making it work needs ~12 edits in `prebuildfs/` and `rootfs/` (the `tr ',;' ' '` splits
become `${var//[,;]/ }`; the RabbitMQ Erlang cookie and password salt need `openssl rand`
and `head -c`). Those are exactly the files that must stay byte-identical to upstream for a
clean rebase: **Dockerfile-level divergence is free here, script-level divergence is not.**

Two traps if anyone does revisit it: `busybox --install` symlinks *every* applet and
shadows the real `dpkg`, `grep` and `find`; and `<applet-list> | grep -qx` under `pipefail`
reports failure for the names that *do* match, because `grep -q` exits early and the
producer dies of SIGPIPE — which silently yields an empty applet list.

## Build and verify

```console
cd 4.3/wolfi
docker build --provenance=false --sbom=false -t bitnami-rabbitmq:4.3.5-wolfi-r1 .
```

`--provenance=false --sbom=false` matters: with default attestations, Docker 29 writes an
OCI layout that Trivy 0.74 rejects with `archive/tar: invalid tar header`.

No source compilation happens in this variant, so both legs are cheap — an emulated
`linux/amd64` build on Apple Silicon is a few minutes, not the 20+ the old Erlang source
build cost:

```console
docker buildx build --platform linux/amd64,linux/arm64 \
  -t insightfinderinc/bitnami-rabbitmq:4.3.5-wolfi-r1 --push .
```

Scan. **No scanner can read the daemon's image directly here** — Trivy and Docker Scout
both fail on Docker 29's OCI layout with `archive/tar: invalid tar header` or `unexpected
EOF`. This is a Docker 29 limitation, not a scanner one; scanning a pushed registry
reference works. Locally, go through the exported filesystem:

```console
docker create --name probe bitnami-rabbitmq:4.3.5-wolfi-r1
mkdir fs && docker export probe | tar -x -C fs && docker rm -f probe

trivy rootfs --scanners vuln fs                    # all severities
trivy rootfs --scanners vuln --ignore-unfixed fs   # the pass condition: must be empty
```

**Use Trivy. grype is not installed on this machine** (decision of 2026-09-15). Compensate
for narrower DB coverage by scanning the `4.3/debian-12` baseline the same way and
comparing per CVE ID — a before/after delta is the real evidence, and it stays valid even
where absolute coverage is narrower. Pair a scan with the per-package checks in the
variant's README; some advisories are in no database yet and can only be verified by the
package being absent or at a known version.

The pass condition is **zero fixable findings**, not a zero total.

Smoke test:

```console
docker run -d --name rmq -e RABBITMQ_PASSWORD=bitnami123 -e RABBITMQ_LOGS=- bitnami-rabbitmq:4.3.5-wolfi-r1
docker exec rmq rabbitmq-diagnostics -q check_running
docker exec rmq rabbitmq-diagnostics -q check_port_connectivity
docker exec rmq rabbitmq-diagnostics -q status | grep -E 'RabbitMQ version|Erlang configuration|Crypto library'
docker exec rmq cat /opt/bitnami/erlang/lib/erlang/releases/27/OTP_VERSION
```

Publish/consume through the management API (this also exercises the `wget` call sites), and
confirm the composition assumptions held:

```console
docker exec rmq bash -c 'command -v perl; command -v curl; apk info -v | grep -E "^(acl|attr|zlib)-"'
```

Expect no perl, no curl, and the patched acl/attr/zlib versions.

## Upstream sync

`origin` is the fork, `upstream` is `bitnami/containers`. When pulling upstream releases,
`4.3/debian-12/` moves and `4.3/wolfi/` does not. Everything outside `4.3/wolfi/` is
byte-identical to upstream — keep it that way, including this image's top-level `README.md`
and `docker-compose*.yml`.

After a RabbitMQ release bump, copy `prebuildfs/` and `rootfs/` across from the new
`debian-12` variant, then update the component version and checksums in the wolfi
`Dockerfile` and `prebuildfs/opt/bitnami/checksums/`, and re-apply the four local script
changes on top. `diff -rq 4.3/debian-12 4.3/wolfi` should report exactly:

| path | why it differs |
| --- | --- |
| `Dockerfile`, `docker-compose.yml`, `README.md` | the variant itself |
| `prebuildfs/usr/sbin` → `prebuildfs/usr/bin` | Wolfi symlinks sbin into bin |
| `prebuildfs/opt/bitnami/checksums/erlang-*` (absent here) | Erlang comes from apk, not a Bitnami component |
| `prebuildfs/.../libfile.sh` | `replace_in_file_multiline`: `perl -pe` → `sed -z -E` |
| `prebuildfs/.../libnet.sh` | `wait_for_http_connection`: `curl` → `wget` |
| `rootfs/.../librabbitmq.sh` | plugin download: `curl` → `wget`, plus a `cp` branch for `file://` |
| `rootfs/.../rabbitmq/apicheck.sh` | `curl` → `wget` |

Anything beyond that list is drift. Keep new remediation in the **Dockerfile**: those four
script changes exist only because `curl`/`perl` are not in the image, and every further
line of script divergence costs a rebase conflict every release for nothing.
