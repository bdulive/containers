# bitnami/redis-cluster

## Directory roles

| Path | Role |
| --- | --- |
| `8.10/wolfi/` | **The only hand-maintained variant.** Redis(R) Cluster 8.10.1 on `cgr.dev/chainguard/wolfi-base`. All local remediation goes here. See its `README.md` for the change list and CVE map. |
| `8.10/debian-12/` | **Generated by the Bitnami release pipeline. Do not hand-edit.** Any change here is overwritten on the next `[bitnami/redis-cluster] Release ...` commit from `upstream`. |
| `6.2/`, `7.2/`, `7.4/`, `8.2/`, `8.4/`, `8.8/`, `README.md`, `docker-compose.yml` | Upstream. Leave byte-identical so the fork keeps merging cleanly. |
| `prebuildfs/opt/bitnami/scripts/lib*.sh` (inside each variant) | Shared Bitnami shell libraries, vendored per image. Edits are local to that one variant. |
| `rootfs/opt/bitnami/scripts/librediscluster.sh`, `libredis.sh` | Redis-specific logic: config generation, cluster creation and node join. |
| `prebuildfs/opt/bitnami/checksums/` | `sha256` files for the components the Dockerfile downloads. One file per component per arch; a component removed from the Dockerfile must have its checksum file removed too. |

**Wolfi is where every future CVE fix goes. Do not add a Debian-based variant to carry
one.** No Debian base can clear the acl/attr advisories, and the workarounds a Debian base
would need — a `perl` force-purge, installing `wget` only to purge it again — are simply
unnecessary here. Measured 2026-09-17 against the upstream `debian-12` image built the same
day with the same Trivy DB: 291 findings vs 1.

## Image composition

The wolfi variant assembles three pieces:

1. `cgr.dev/chainguard/wolfi-base`.
2. Prebuilt component tarballs (`redis`, `wait-for-port`) from
   `https://downloads.bitnami.com/files/stacksmith`, named
   `<name>-<version>-<revision>-linux-<arch>-debian-12.tar.gz`, fetched and
   checksum-verified in a **separate build stage**, then unpacked to `/opt/bitnami` with
   `--strip-components=2`.
3. `prebuildfs` and `rootfs` overlays, then `postunpack.sh`.

Facts worth not re-deriving:

- **The `debian-12` `redis` component runs unmodified on Wolfi's glibc.** `redis-server`
  links only against `libm`, `libssl`/`libcrypto`, `libc`, `libz` and `libzstd`, and glibc
  is forward-compatible; `wait-for-port` is Go and needs only `libc`. Bitnami publishes no
  Wolfi components, and none are needed — but the build asserts it rather than assuming it:
  the final layer runs `redis-server --version` and `redis-cli --version` (alongside
  `! command -v perl`) so a glibc or linker mismatch fails the build, not the first boot.
- **No HTTP client is in the runtime image at all.** The one runtime call site,
  `libnet.sh`'s `wait_for_http_connection`, is unreachable in this image — and was already
  broken in `debian-12`, which installs `curl` only to download components and then
  `uninstall_packages` it. Here the download happens in a separate build stage, so `wget`
  and its gnutls/idn2/nettle/psl chain never reach the runtime layer at all. **This is what
  keeps the variant at zero script divergence** (contrast `bitnami/rabbitmq`, whose three
  real HTTP call sites force four local script edits).
- **Perl is not used at runtime, and Wolfi installs none.** `redis_conf_set` goes through
  `replace_in_file`, which uses `sed`. Only `replace_in_file_multiline` used `perl`, and
  nothing in the image calls it. The other `perl` grep hits are the word "properly". No
  `locale-gen` runs here either (unlike a minideb base), so nothing drags perl back in; the
  build asserts `! command -v perl` at the end. This image installs no locale package at
  all and sets no `LANG` — redis needs none. rabbitmq does, and pulls `glibc-locale-en`.
- **The `openssl` CLI is not needed** — unlike rabbitmq, nothing here hashes passwords with
  it.
- **GNU userland is installed deliberately** (`coreutils sed grep gawk findutils`). The
  Bitnami script library depends on GNU behaviour; on Wolfi it costs nothing in CVE terms
  because those packages pull the *patched* acl/attr.
- `getent` comes from `posix-libc-utils-bin`; `wolfi-base` only ships `nonroot` (65532), so
  uid 1001 is created explicitly; prebuildfs helpers live under `usr/bin`, not `usr/sbin`,
  because Wolfi symlinks `/usr/sbin` and `/sbin` to `usr/bin` and `COPY` cannot write
  through a symlinked directory.
- **The 6-node `docker-compose.yml` is the real smoke test**, not a single container:
  node-5 carries `REDIS_CLUSTER_CREATOR=yes` and bootstraps the cluster once the other five
  are up.

## CVE remediation workflow

Work in this order; each step tells you whether the next is even needed.

1. **Check the Wolfi secdb before anything else.** Wolfi's fix is usually already
   packaged, and often under a version string the scanner does not expect:

   ```console
   curl -sS https://packages.wolfi.dev/os/security.json | \
     jq '.packages[] | select(.pkg.name=="<pkg>") | .pkg.secfixes'
   ```

   If the secdb names a fixed version at or below what `apk` installs, a plain rebuild is
   the fix — and if the scanner still reports it, see the zlib section below before
   touching the Dockerfile.
2. **Rebuild first.** `apk upgrade --no-cache` runs in the Dockerfile, so a rebuild picks
   up every published fix. Bump `IMAGE_REVISION` and the `-r<n>` tag; that is the whole
   change for most advisories.
3. **Check what Bitnami components exist before assuming a component bump is possible.**
   Bitnami publishes for base releases only. Probe before planning:
   `curl -o /dev/null -w '%{http_code}' https://downloads.bitnami.com/files/stacksmith/redis-<ver>-<rev>-linux-amd64-debian-12.tar.gz.sha256`
4. **Read an advisory's affected range against the *upstream* version, not a distro's.**
   Distro matchers key on the suite: a feed with no fixed version flags the package at
   *any* version with no `FixedVersion`. Confirm with
   `trivy rootfs --format json fs | jq '.Results[].Vulnerabilities[]? | select(.VulnerabilityID=="CVE-...")'`
   before concluding an upgrade failed.

### Why the base is Wolfi: the acl/attr advisories

`8.10/wolfi/` clears CVE-2026-54369/-54370/-54371 for real. Chainguard packages the
**fixed** upstream releases — `libacl1 2.4.0-r3` and `libattr1 2.6.0-r3` — which Debian has
only in forky/sid. On any Debian base `libacl1` is unavoidable: it arrives via `coreutils`,
`passwd`, `sed` and `tar`, and trixie is pinned to the unfixed acl 2.3.2 / attr 2.5.2,
marked `no-dsa` with the fix landing in unstable first. Docker Hardened Images do not fix
them either — DHI rebuilds the same unfixed sources and waives the findings with an
OpenVEX `not_affected` statement, so any scanner that does not consume that VEX still
reports all three. **Do not re-propose a Debian or DHI base.**

### CVE-2026-85091 (zlib): fixed in the package, still reported by Trivy

The `-r0` image shipped `zlib 1.3.2-r6`, inside the advisory's range, with the fix named as
a version (`1.3.3-r0`) that had not reached the apk repo. **That identifier was
superseded.** Chainguard backported the fix instead — upstream `madler/zlib` commit
`df84af25dc` ("Fix buffer overflow bug in non-blocking gzwrite"), carried as
`0001-gz_write-don-t-keep-a-pointer-into-callers-buffer-on.patch` in `zlib.yaml` — and both
`packages.wolfi.dev/os/security.json` and `packages.cgr.dev/chainguard/security.json` now
name the fixed version as **`1.3.2.1_rc20260601-r0`**, which is what `apk` installs today.
The `-r1` rebuild (2026-09-17) carries it, and Docker Scout reports 0 findings on it.

**Do not wait for a zlib 1.3.3 package.** Upstream has no such tag; `v1.3.2` is the newest,
and `1.3.2.1_rc20260601` is a develop-branch snapshot Chainguard versioned with an `_rc`
suffix deliberately so a future real 1.3.2.1 sorts above it.

Trivy 0.74 still emits the row: its DB (built 2026-09-16 19:39 UTC) carries the stale
`1.3.3-r0` fixed-version, above the installed one. This is scanner-DB lag, not package
state, and it should clear on a later DB build with no image change. **Re-check with
`trivy image --download-db-only` and rescan before treating it as a real finding**, and
compare the installed version against the secdb query in step 1 before concluding a
rebuild is needed.

Do not pin zlib backwards to dodge any of this: `1.3.1.2-r3` is still inside the range
*and* adds CVE-2026-27171.

### Do not retry: swapping the GNU userland for applets

Prototyped and rejected on 2026-09-14, when the goal was shedding `libacl1`/`libattr1` on a
Debian base. **On Wolfi the premise is gone** — the GNU packages pull the *patched*
acl/attr. The measurements are kept because the conclusion generalises:

| replacement | scanner total / CRITICAL / HIGH (grype, pre-2026-09-15, on the Debian base) | verdict |
| --- | --- | --- |
| none | 139 / 0 / 44 | the three acl/attr rows are reported |
| busybox 1.37.0 | 140 / 0 / 50 | rows gone, but busybox adds **14 advisories of its own, 8 HIGH, all wont-fix** |
| toybox 0.8.9 | 126 / 0 / 42 | rows gone, toybox carries **zero** CVEs — but it has no `tr` or `dd` |

toybox was the only version worth having and it could not ship: the Bitnami scripts use
`tr` on live paths and the failure is **silent**, not loud. `run.sh` parses `REDIS_NODES`
through `tr`, so the container still starts and Redis still boots, with an empty node list
and `Cluster topology covers 0 of 16384 slots`:

```text
toybox image -> parsed 0 nodes: []
GNU userland -> parsed 6 nodes: [n0 n1 n2 n3 n4 n5]
```

Making it work needs ~12 edits in `prebuildfs/` and `rootfs/` (the `tr ',;' ' '` splits
become `${var//[,;]/ }`). Those are exactly the files that must stay byte-identical to
upstream for a clean rebase — and this variant currently has **zero** script divergence,
which is worth protecting: **Dockerfile-level divergence is free here, script-level
divergence is not.**

Two traps if anyone does revisit it: `busybox --install` symlinks *every* applet and
shadows the real `grep` and `find`; and `<applet-list> | grep -qx` under `pipefail` reports
failure for the names that *do* match, because `grep -q` exits early and the producer dies
of SIGPIPE — which silently yields an empty applet list.

## Build and verify

```console
cd 8.10/wolfi
docker build --provenance=false --sbom=false -t bitnami-redis-cluster:8.10.1-wolfi-r1 .
```

`--provenance=false --sbom=false` matters: with default attestations, Docker 29 writes an
OCI layout that Trivy 0.74 rejects with `archive/tar: invalid tar header`.

On Apple Silicon build `linux/arm64` natively for functional iteration. Emulated
`linux/amd64` is cheap for this image (prebuilt components only, no compilation), so build
and scan both legs before publishing:

```console
docker buildx build --platform linux/amd64,linux/arm64 \
  -t insightfinderinc/bitnami-redis-cluster:8.10.1-wolfi-r1 --push .
```

Both architectures should report identical Trivy totals; a divergence means an
arch-specific package slipped in.

Scan through the *exported filesystem*: Docker 29 writes an OCI layout that **every**
scanner rejects when reading the daemon image directly (`archive/tar: invalid tar header`,
or `unexpected EOF`). Scanning a pushed registry reference works; only the local daemon
image needs the export.

```console
docker create --name probe bitnami-redis-cluster:8.10.1-wolfi-r1
mkdir fs && docker export probe | tar -x -C fs && docker rm -f probe

trivy rootfs --scanners vuln fs                    # all severities
trivy rootfs --scanners vuln --ignore-unfixed fs   # the pass condition: must be empty
```

**Use Trivy. grype is not installed on this machine** (decision of 2026-09-15). Compensate
for narrower DB coverage by scanning the `8.10/debian-12` baseline the same way and
comparing per CVE ID — a before/after delta is the real evidence, and it stays valid even
where absolute coverage is narrower.

Treat a finding as actionable only if a fix exists — a non-empty `FixedVersion`, which is
what `--ignore-unfixed` filters on. The pass condition is **zero fixable findings**, not a
zero total.

Smoke test with the real 6-node cluster, not a single container — cluster bootstrap is the
part most likely to break:

```console
docker compose -p rcverify up -d
docker exec rcverify-redis-node-0-1 redis-cli -a bitnami --no-auth-warning cluster info
# expect cluster_state:ok, cluster_known_nodes:6, cluster_slots_assigned:16384
docker exec rcverify-redis-node-0-1 redis-cli -c -a bitnami --no-auth-warning set alpha val
docker exec rcverify-redis-node-2-1 redis-cli -c -a bitnami --no-auth-warning get alpha
docker compose -p rcverify down -v
```

And confirm the composition assumptions held:

```console
docker run --rm --entrypoint bash bitnami-redis-cluster:8.10.1-wolfi-r1 -c \
  'command -v perl; command -v curl; command -v wget; apk info -v | grep -E "^(libacl1|libattr1|zlib)-"'
```

Expect no perl, no curl, no wget, and `libacl1-2.4.0-r3`, `libattr1-2.6.0-r3`,
`zlib-1.3.2.1_rc20260601-r0`. The packages are named `libacl1` and `libattr1`, not
`acl`/`attr` — a `^(acl|attr)` pattern matches nothing and reads as a pass.

## Upstream sync

`origin` is the fork, `upstream` is `bitnami/containers`. When pulling upstream releases,
`8.10/debian-12/` moves and `8.10/wolfi/` does not. Everything outside `8.10/wolfi/` is
byte-identical to upstream — keep it that way, including this image's top-level `README.md`
and `docker-compose.yml`.

After a Redis release bump, copy `prebuildfs/` and `rootfs/` across from the new
`debian-12` variant **verbatim** — there are deliberately no local script changes — then
update the component version and checksums in the wolfi `Dockerfile` and
`prebuildfs/opt/bitnami/checksums/`. `diff -rq 8.10/debian-12 8.10/wolfi` should report
only `Dockerfile`, `docker-compose.yml`, `README.md` and the `prebuildfs/usr/sbin` →
`prebuildfs/usr/bin` move. Anything else is drift.

Keep it that way. Only the Dockerfile carries the remediation; edits to the shared
libraries buy nothing for the CVE result and cost a rebase conflict every release. The two
functions that reference the removed `perl` and HTTP client are unreachable in this image —
see the variant README.
